Stack Benchmarking

Ryan Stevens

Introduction

Closing the books is one of the most important recurring workflows for any accounting team. At the end of each month, accountants need to verify transactions, reconcile accounts, investigate discrepancies, collect missing documentation, prepare journal entries, and make sure the financial statements are accurate before reporting begins. Much of this work is still painfully manual: downloading reports from different systems, matching transactions one by one, checking whether accruals are complete, and explaining why balances changed from the prior period. These steps are necessary, but they are also repetitive, time-sensitive, and easy to slow down when information is scattered across tools.

Ramp Stack was built to give accountants their time back. Stack is a suite of AI-native tools built to automate manual accounting work. At its core is an optimized AI Agent capable of solving complex book-closing tasks. Accountants can interact with this agent via a chat-based interface or schedule it to handle regular book close items on a recurring basis. This post will cover how we developed a benchmark to help us improve our agent.

The agent sits at the core of Stack

Cold Starting an Agent

Our goal with Stack was to build the best agentic experience for accountants. Traditionally, early product development happens with design partners. These partnerships help you build intuition about customer needs and understand how your product aligns with customer expectations. You iterate on code as your design partner's feedback comes in.

For agentic accounting work, that loop has pitfalls. Accounting workflows vary widely by customer, so it is easy to overfit the agent to a single design partner's environment. The feedback loop is also slow and imprecise: you change the prompt or tool, wait for users to hit the same case again, and then infer whether the change helped.

A benchmark solves these issues. A benchmark is equivalent to an offline dataset that machine learning engineers use to train models. It is a static snapshot of the world that you can hill climb against before having customers interact with the model. It lets us test the same agent against many business types and many accounting tasks, and it gives us fast, comparable feedback when we change a model, prompt, tool, skill, or memory system. Even after launch, the same benchmark can catch regressions, identify where the agent is improving, and show where our next iteration should focus.

Introducing Ramp's Accounting Benchmark

To quickly improve our agent, Ramp developed an accounting benchmark that mimics real book closes. We created complex synthetic businesses, real accounting tasks, and used real-life accountants to develop criteria for grading task runs. We used this dataset to pick the right frontier model, iterate on our harness, and optimize our agent before putting it in front of customers.

Our benchmark consists of two primary objects:

  • World: a synthetic business, including the state of the customer's accounting software (such as QuickBooks) and other files relevant to a book close
  • Tasks: specific accounting jobs to be done inside that world

Here is one representative task:

Compare October 2024 to July 2024. Find the top 5 variances. Classify each as seasonal or unexpected, and explain the driver.

For that task, the agent may need to pull a P&L, inspect GL detail, read an inventory planning model, and compare the output against the annual budget. The task is graded against multiple accountant-written criteria, such as "identifies Total Revenue as a top-five variance" or "correctly classifies October marketing as unexpected." A task score is the fraction of the grading criteria the response satisfies.

Accounting has many repetitive tasks where the process is the same and only the data changes. Stack has a custom-built memory architecture that tracks users' processes and ensures tasks are executed consistently each month. We wanted to build a benchmark that allows us to both iterate on and measure our memory architecture. Thus, we created two different types of worlds:

  • Standard worlds: synthetic businesses with realistic transaction histories, files, and close tasks
  • Roll-forward worlds: a synthetic business advanced to a future time period, used to test whether memory transfers without contaminating the next period's work

We created tasks of four different types that represent the general sets of tasks done during book closes:

  • Reconciliation: tie two sources together, identify differences, and explain or correct the breaks.
  • Data Entry: post or update transactions, journal entries, vendor bills, invoices, or other close data.
  • Variance Analysis: compare actuals against budget, prior periods, or expectations and explain the drivers.
  • Schedules and Accruals: build or update supporting schedules, calculate accruals, and carry the right balances into the close.

How We Optimized Ramp Stack

Stack combines an agentic harness, tools, custom-built skills, and a memory system. At the heart of Stack is a foundation model. In this write-up, we will be using GPT 5.5 for benchmarking.

Before we created the benchmark, Stack already had an initial system prompt, a set of hand-written skills, and its memory system. The benchmark gave us a way to decide what to keep, prune, or rewrite.

The benchmark quickly gave us two guiding principles:

  • Reduce unnecessary context bloat to improve model performance
  • Tune the harness against end-to-end task performance, not just narrow evals

We will discuss the two major ways we optimized Stack.

Reducing Unnecessary Bloat: Skill Ablation and Skill Fine-Tuning

Agent systems tend to accumulate too many skills, and those skills tend to get too long. One of the most important jobs was to figure out which capabilities actually mattered.

Being an ML engineer, I treated this like feature selection. We removed all skills, then ran separate benchmarks where the agent could load only one skill at a time. This gave us a marginal performance estimate for each skill.

Average skill impact

We anonymize the individual skill names here, but each represents a different agent capability. The result was not that every skill helped. Only Skill A and Skill B were positive on average. Skill C was essentially neutral. The rest were negative on average, and none was uniformly best across worlds. That finding let us prune the bundle rather than carry every piece of context forward.

When we combined the retained skills into a slim bundle, the aggregate effect was generally positive:

4-skill bundle impact by world

The bundle helped meaningfully on world_4 and world_5, helped modestly on world_3, and was roughly flat or slightly negative on the other worlds. Across the six standard worlds, the slim bundle was +2.3 percentage points versus the no-skills baseline in the current cleaned snapshot. That pattern is exactly why we needed the benchmark: a single task or a single world would have produced the wrong intuition.

An additional exercise was to shrink the largest high-load skill. We had a custom spreadsheet skill used for spreadsheet manipulation. It loaded in many sessions and came in at 14k characters. Roughly half of it was financial modeling guidance that was not relevant to bookkeeping close work.

We split that skill into two and reduced the content of the spreadsheet skill. The bookkeeping spreadsheet skill went from 14k characters to 5k characters, a 64% reduction. The removed content moved into a separate, narrower module for the workflows that actually need it. In a paired validation on a single world, the original spreadsheet skill and slim spreadsheet skill landed in the same place: +3.7 percentage points versus baseline for the original version and +3.3 percentage points for the slim version. The full slim bundle reached +5.4 percentage points on the same world.

The important point is that shrinking the context was not just cleanup work. It also made the prompt easier to reason about. We kept the behavior that mattered for bookkeeping and stopped loading guidance that belonged to a different product surface.

Harness Tuning: Our Memory System

A key part of the agentic experience is memory: users should not have to re-teach the agent the same company context every session. The hard question is what facts are safe to write down.

The first version of this idea was too optimistic. We gave a memory writer the prior task and the correct answer, and hoped the agent would infer the reusable playbook on its own. That produced plausible summaries, but it did not reliably preserve the actual steps an accountant should take. The model could remember what happened, but not always how to reproduce it.

We then moved toward step-oriented memory. Instead of asking the writer to infer everything from task and answer alone, we used task trajectories and step-by-step guides to extract the pieces that should transfer to a future period: source-file mappings, schedule structure, GL account names, calculation methods, and validation checks. The memo is injected into a related future-period task, where the benchmark can measure whether that handoff helps or hurts.

Memory on vs. off

On our roll-forward world, memory improved mean score from 56.0% to 61.5%, a +5.5 percentage point gain. The strategies that worked had a common shape: they captured reusable process without overfitting to the old period. The cleanest example was a workers' compensation audit estimate. The future-period task asked the agent to refresh Granite Peak's January 2025 workers' comp accrual. Without memory, the agent scored 0%. With memory, it scored 100%.

Here is the memory that was written from the prior-period task:

Pull Aug-Dec 2024 actual wages from GL_Detail.xlsx for account 5010 Field Labor and account 6000 G&A Wages, correcting for any unreversed prior-period payroll accrual that would double-count. Annualize the corrected payroll on a 12/5 basis. Read the workers' comp policy to extract class codes, class-mix proportions, per-$100 rates, the experience modification factor, and the paid premium. Allocate annualized payroll across class codes, apply the rates and experience modification, subtract the paid policy premium, compute the accrual share, compare it to any existing WC audit accrual, allocate the accrual to projects, and propose the journal entry: debit Insurance Allocated and credit Accrued Project Costs.

That memory still contains prior-period details, but the transferable part is strong: it tells the agent which GL accounts matter, which policy fields drive the calculation, how to shape the estimate, and what the final accounting treatment should be. It is a reusable workflow, not just an old answer.

The strategies that hurt had the opposite shape: the memo smuggled in the old task's fact pattern. In the Apex January AIA billing task, the no-memory agent scored 75%, while the memory-enabled agent fell to 25%. The January task required reviewing the current AIA progress billing and deciding whether any adjustments were needed. This is the memory the agent received:

Read Owner_Contracts_and_Change_Orders.pdf to identify the approved Apex CO-001 and the associated HVAC controls billing amount. Review the AIA pay application to confirm that CO-001 billing has been included and that the corresponding revenue is already recognized to Contract Asset. Review QBO_Invoices.csv to confirm what has already been posted for CO-001 and determine what remains to be booked. Pull the contractual retention rate from Retention_Schedule_Nov2024.xlsx. Split the CO-001 billing amount into Retention Receivable and net Accounts Receivable. Propose the reclassification journal entry: debit Accounts Receivable and Retention Receivable, credit Contract Asset.

Those instructions were reasonable for the prior task, but too specific for the roll-forward. The memory pushed the agent toward an older CO-001 reclassification recipe, and the agent followed it too literally.

That changed the memory strategy. The goal is not "always write more memory." The goal is to write memories that generalize: stable account mappings, source-file conventions, workflow patterns, and explicit steps. Period-specific amounts, customer lists, file names, old contract terms, and one-off recipes need stronger filtering or task-level opt-out. The benchmark made the failure mode obvious: if we do not give the memory writer the steps, it cannot be trusted to reconstruct them from task and answer alone.

How Stack Compares to Frontier Models

Performance

Our first exercise was to assess how Ramp Stack performs. To benchmark against frontier models, we stripped Ramp Stack of its skills and its memory system. When we report a frontier model, it is running in the no-skill, no-memory harness. Ramp Stack is a frontier model (GPT 5.5) that includes skills and a memory system. This allows us to isolate the performance impact of our skill and memory optimizations.

We measured four performance metrics:

  • Pass@1: a single attempt fully satisfies all criteria on a task
  • Pass@5: at least one of five independent attempts fully satisfies all criteria on a task
  • Pass^5: all five independent attempts fully satisfy all criteria on a task, which is a stricter measure of consistency
  • Mean Criteria Accuracy: the average fraction of grading criteria satisfied across runs

This is one reason the benchmark is useful. The aggregate score tells us which model is strongest overall, but the task-category view tells us where the agent actually needs help. Schedules and accruals are materially harder than variance analysis for the raw models, while reconciliation is relatively strong for the best models. Ramp Stack improves every category, with the largest absolute lift on variance analysis and reconciliation. Our hypothesis is that reconciliation maps more naturally to a general comparison task: compare one system of record against another, identify the delta, and explain it. Schedules and accruals are more accounting-specific, more procedural, and often require a longer-horizon context.

User-Facing Tradeoffs

Performance is only one metric that matters for an agent. Users also care about latency. We therefore consider an additional tradeoff: accuracy versus runtime. Each point represents a model or system choice, and the frontier shows where we can buy more performance only by giving up speed.

To measure latency, we use the runtime per task. Runtime is measured from task trajectory timestamps, not from parent-flow wall clock time divided by task count, so it captures the end-to-end task experience: model calls, tool use, file processing, and waiting during the run.

Conclusion

The benchmark became our development loop for Stack. It let us make decisions that would otherwise have been vibes-based: which frontier models were worth using, how to balance accuracy against latency, which skills helped or hurt, when memory generalized, and where additional reasoning effort did not justify its complexity.

The broader lesson is that agent development needs the same discipline as ML development. You need a dataset that is hard enough to be meaningful, stable enough to compare runs, and detailed enough to explain why a change worked. Once you have that, the benchmark stops being a scoreboard and starts becoming a product development engine.
