Online Learning for Cost-Efficient LLM Routing

Kedar Thakkar

Summary

At Ramp, we've built our own internal LLM gateway that processes trillions of tokens per day, serving all of the various ways we use AI both for internal development and for external products. Operating as a single centralized point through which all AI usage goes requires a heavy emphasis on reliability and efficiency, but also unlocks opportunities to attribute spend in an organized manner and to optimize it where possible.

With that in mind, in the rest of this post I'll discuss one strategy we've used to cut our AI spend by more than 25% while simultaneously reducing our error rate, through dynamic failure-aware routing across models and service tiers.

Roots

The idea started with staring at some graphs that Rahul, our CTO, pulled up to show that OpenAI's flex tier was not always higher latency than default like we'd previously assumed.

It solidified into a hypothesis after chatting with a customer (shoutout Mercana) who mentioned that outside of business hours standard and flex tiers were pretty similar, but latency for flex quickly degraded 9am-5pm.

Optimizing for this wasn't straightforward though, because the patterns weren't immediately obvious and so any strategy to optimally route across service tiers would have to be dynamic and adaptive. From there came the idea: why not learn the real-time latency and failure distribution online?

Branches

Stepping back for a second, let's chat philosophically about what we at Ramp care about when making an LLM request, and why latency is important. The core tenets are:

  • Reliability is the top priority. LLMs fail for many reasons: provider outages, rate limiting, server-side errors, etc. We design our products to be robust to failures, but still prefer to avoid them as much as possible.
  • Latency is a key component of reliability that's very caller and use-case specific. For an automation that runs in the background, latency doesn't matter at all. For an invoice processing flow that displays a "Loading..." spinner to the user until it completes, latency degradation is as painful as a failure.
  • Callers represent model preference via the model priority order they send to the gateway. For example, an agent that replies to SMS might prefer the stylistic output of Claude Opus 4.8, but is ok falling back to GPT 5.6 when necessary.

Now let's talk about how we decided to encode all of that into a single routing strategy:

We start by taking the EWMA (exponentially-weighted moving average) of failure rate, including only genuine provider-side failures (we shouldn't penalize a model because a caller sent an invalid request). This looks something like the following when we're getting rate limited by Vertex AI:

Then, learn the point-in-time latency distribution through Thompson Sampling, optimally trading off exploration and exploitation. For each context slice, the evolution looks something like this:

To do that we put a conjugate Normal-Inverse-Gamma (NIG) prior on the unknown mean and variance of log-latency, (μ, σ²). Using pooled sufficient statistics stored in Redis, we update the posterior of this distribution as follows:

κₙ = κ₀ + n
μₙ = (κ₀·μ₀ + n·meanLog) / κₙ
αₙ = α₀ + n/2
βₙ = β₀ + 0.5·deviationSum + (κ₀·n·(meanLog − μ₀)²) / (2·κₙ)

Now, when it comes time to choose which model to route to for a given request, we start by sampling. Routing to a given model is a bad outcome if it either fails outright, or — conditional on not failing — still misses the deadline:

P(bad_outcome) = P(failure) + (1 − P(failure)) · P(latency > deadline)

We get P(failure) from the earlier EWMA failure rate and P(latency > deadline) by sampling μ and σ², and calculating the area under the curve of the distribution from deadline onwards. We combine this with the relative cost of that model, to assign each model option a score. From there, simply sort the list and try the first model, falling back if necessary.

Fruits

We started by shipping this to the an LLM reranker use case which has a tight (6-second) deadline and the following preference list:

  • Gemini 3.1 Flash Lite Standard
  • GPT 5.4 Nano Standard

We expanded that preference list to the following and passed it to our routing strategy to reorder as desired:

  • Gemini 3.1 Flash Lite Flex
  • Gemini 3.1 Flash Lite Standard
  • Gemini 3.1 Flash Lite Priority
  • GPT 5.4 Nano Flex
  • GPT 5.4 Nano Standard

We happened to deploy during a period of high rate limiting on Gemini 3.1 Flash Lite, and immediately saw rerouting to GPT 5.4 Nano, followed by a reversion back to Gemini 3.1 Flash Lite after it had recovered:

Interestingly, we saw that requests were rerouted to GPT 5.4 Nano Flex, not Standard! I looked into it further and during that time period, latencies were almost identical between the two and both were well under the reranker's 6 second timeout so going with the half-price option was the optimal decision.
