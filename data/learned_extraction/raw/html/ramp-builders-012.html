We proactively fixed ~100 security issues in 6 days with 0 humans

Eli Block

Ramp Security Engineering proactively found, validated, and fixed nearly 100 latent security issues in our backend codebase without a human in the loop (until PR review) by deploying a team of home-grown agents and a bit of queuing.

The fixed issues were novel: they had not been uncovered previously by penetration testing, bug bounty testing, static analysis, or trials from 10+ code-scanning vendors. Some of the issues were high severity. All were patched within a week of discovery.

A four-hour hackathon and less than a week of work by one member of our team made the product more secure for our customers. Your team can do this next week for your customers. Alternatively, Ramp is hiring, come build with us.

Why did we build this?

Security Engineering exists to earn trust from Ramp customers. Our team accelerates Ramp engineering via secure-by-default foundations, builds guardrails to detect and mitigate abnormal behavior, and helps out when things go wrong.

Many security teams in the industry operate in a different way, running tooling-based security programs. Instead of the guardrails-based approach we take, tooling-based teams spend attention and time using tooling to detect potential issues and then resolving them. These programs tend to operate something like this:

  1. Find: Identify potential issues via scans or other tooling.
  2. Validate: Make sure the potential issue is reproducible and might impact the environment.
  3. Fix: Patch the issue or fix the root cause.
  4. Confirm: Check that the fix addressed the validated finding.

Steps 2, 3, and 4 are all labor intensive. There are typically handoffs between teams for each step, producing organizational bottlenecks.

Even a real finding which is low-impact wastes security team time validating the finding, developer time fixing it, and security team time confirming it. Burning this much effort on low-impact findings also erodes organizational trust in the security team: why are they fixated on a non-issue instead of moving the business forward? Some tooling-based teams mitigate this by acting on only critical or high severity issues, leaving the rest unpatched.

Agents dramatically lower the costs of a tooling-based security program. When the program no longer requires human time—instead costing merely tokens to validate, fix, and confirm a finding—it is possible to act on a broad set of potential issues without the labor or organizational-trust costs. Doing so makes your product more secure; you might find some serious issues like we did!

Why not buy this product?

There are dozens of security companies currently leveraging LLMs to supplement or replace static analysis and human testing. Foundational labs are getting involved as well, with OpenAI’s Aardvark, Anthropic’s Security Review, Google’s CodeMender (not publicly released), and rumors of more on the way. At Ramp we’ve demoed or trialed products from 10+ companies in this space.

These companies haven’t been building for long, and the products seem largely undifferentiated. While, in the future, sophisticated techniques may give these companies the edge, at the moment your team has the advantage: context. You already know how to accurately find, validate, fix, and confirm vulnerabilities in your environment, and you know what vulnerabilities are most impactful. Similarly to how Ramp Inspect operates more like a Ramp engineer than any public coding agent could, a home-grown team of security agents fits your specific environment, priorities, and threat model better than anything on the market today.

How to build your own

We ran this as a quick experiment. If we were to rebuild it, our architecture would evolve, but the core patterns would hold:

  • Leverage specialized detectors, “experts” in particular vulnerability classes.
  • Apply adversarial managers, “judges” who iterate on a finding with a detector before reporting it.
  • Write integration tests for validation and confirmation.

Detector-manager pattern

To start our agentic pipeline we launched a coordinator agent equipped with skills for each of the vulnerability categories we were targeting. The coordinator launched detector agents in parallel, one for each skill. Specific detectors with focused context windows yielded significantly higher-signal initial findings that more generic prompts or multi-purpose detectors.

We generated our detector skills by combining specific information about a vulnerability class (definition, steps a human analyst would take to find the vulnerability, common impact) with real examples of that vulnerability class from our codebase. We tuned each skill by adjusting the analysis steps or providing more examples.

Detector—Insecure Direct Object Reference
# IDOR Detection Agent
You are a specialized security agent focused on detecting Insecure Direct Object Reference (IDOR) vulnerabilities in the codebase.

## What is IDOR?
IDOR occurs when an application provides direct access to objects based on user-supplied input (like IDs) without proper authorization checks. In a multi-tenant architecture, this may mean accessing resources without verifying that they belong to the authenticated user's tenant.

If the application filters by a user ID sourced directly from the authentication system (not user-supplied input), the endpoint is NOT vulnerable to cross-tenant IDOR (even without an explicit tenant ID check).

## Your Task
Analyze the provided route for IDOR vulnerabilities by:
1. **Reading the source code** using Read and Grep tools
2. **Identifying resource access patterns**
3. **Verifying tenant_id checks** are present
4. **Testing for bypass opportunities**

## Detection Patterns
### 🔴 VULNERABLE Patterns
```python
# Missing tenant_id check entirely
account = get_account_by_id(id)

# Tenant filter is used but the context is untrusted
tenant = Tenant.query.filter_by(tenant_domain="ramp.com")
account = get_account_by_id_and_tenant_id(id=id, tenant_id=tenant.id)

# Authorization check but bypassable
if account and account.tenant_id != g.authenticated_tenant_id:
  # But what if account is None? Bypassed!
  raise Unauthorized()
```

### ✅ SECURE Patterns
```python
# Tenant-scoped query function
account = get_account_by_id_and_tenant_id(
  id=id,
  tenant_id=g.authenticated_tenant_id
)

# Explicit tenant_id filter in query
account = Account.query.filter_by(
  id=transaction_id,
  tenant_id=g.authenticated_tenant_id
).first_or_404()

# Proper null check before authorization
# Even though untrusted data is loaded, we check authorization immediately after:
# there are no side effects or data leaks
account = get_account_by_id(id=id)
if not account or account.tenant_id != g.authenticated_tenant_id:
  raise Unauthorized()

# g.authenticated_user_id is used even though no tenant_id is
account = Account.query.filter_by(
  id=id,
  user_id=g.authenticated_user_id
).first_or_404()

# or…
return AccountSettingsGetSchema().dump(
  {"account": account_settings_for_user_id(g.authenticated_user_id)}
)
```

When a detector found a potential issue, the coordinator passed its output to a manager. These adversarial agents critiqued potential findings, resulting in more actionable reports and a lower rate of false positives. In our intial testing on a sample set of findings, managers rejected 40% of the original proposals, all of which were confirmed to be false positives by a human review.

The validator’s feedback to detectors mimicked what a human analyst might say:

...If the detector wants to report on IDOR protections, they should focus on actual vulnerabilities, not secure implementations with theoretical edge cases that don't apply to the endpoint being tested...

...If an attacker needs direct database access to exploit this vulnerability, they already have much more powerful capabilities than just reading cross-business user data...

We generated our manager skills with common validation steps as well as specific areas to check for each detector. In our experiment managers used only code-reading skills. In the future we will experiment with allowing managers to write and run code as well, pulling forward some of the validation steps described below.

Apply the following overall checklist to all inputs. Additionally, apply the relevant vulnerability-specific checklists

## Overall Checklist
CHECKLIST:
- [ ] The vulnerability described is explained in plain language, and is easy for a human to understand.
- [ ] The vulnerability includes specific code references with filenames and line numbers, and they are accurate.
- [ ] The vulnerability description includes a "so what" describing the impact of the vulnerability.
- [ ] Reject all "best practice" findings which are not exploitable (e.g., if vulnerable data is loaded on line 5 but then errors on line 6, a user is not able to exploit the vulnerability).
- [ ] Reject all timing attacks.
- [ ] Reject all findings that are about an endpoint _other than_ the one being targeted. These will confuse the human analyst.
- [ ] Ensure a fix is suggested for all findings.


## Vulnerability-specific Checklists
### IDOR
IDOR Checklist:
- [ ] Reject any vulnerabilities which are mitigated elsewhere in the callstack for that endpoint.
- [ ] Reject any vulnerabilities which involve accessing data that is _intentionally_ shared across tenants, like the Logos model. If you're unsure, read the code relevant to that data type to determine if it is intentionally cross-business.
- [ ] Reject any vulnerabilities that are about enumeration by status code (e.g., returning 403 instead of 404) if the identifier being enumerated is a UUID. These are not practical to exploit, you'd already need the UUID in order to exploit it. Keep ones with integer or natural keys.

Validation

Interactive testing

At the beginning of our experiment we built a way for agents to interact with a live Ramp deployment on behalf of multiple users at a time. We planned to have an agent reproduce findings with real API requests: the ultimate validation that a finding is real.

Our setup technically worked. The agent was able to validate simple issues. Unfortunately, any remotely complex pre-condition (e.g., "the victim has two funds") proved difficult for the agent to configure and test. Given the strengths of other validation approaches we experimented with, we eventually abandoned this one.

All was not lost! Our human team now uses the setup we originally built for the agent to accelerate our own vulnerability validation.

Test-based validation

While validating findings with complex pre-conditions against a live Ramp deployment proved difficult, it was straightforward to validate them in code. Our validator agent took a reported finding and wrote an integration test that reproduced the vulnerability but would pass only if the endpoint was secure. If the test failed, the finding was validated. If the test already passed before making a code change, the finding was a a false positive.

This approach captured nearly all of the false positive findings produced earlier in the triage pipeline.

Validator
The following analysis records a security vulnerability in an endpoint. Validate the vulnerability by writing tests.

Validation process:
1. Locate and read existing tests for the target endpoint.
2. Write a test that reproduces the vulnerability but asserts the secure result (how the app should behave). Place the tests in the same file as other tests for the target endpoint, copying local style.
a. Wherever possible, write the test at the _endpoint_ level (not a service function level). Always reproduce the vulnerability as an attacker would.
3. Run the test, and confirm it fails. This means the vulnerability is present.
a. If the test does NOT fail, stop here. Do not make any code changes if the test is already passing. If this is the case, return only the string FALSE_POSTIVE, and no other text.
b. If the test fails in a surprising way (e.g., an endpoint 500s), your test is wrong. Update your test to better match the vulnerability report, and continue iterating until the vulnerability is reproduced or confirmed to not exist.
4. Once you have a test which fails due to the vulnerability, return the test case to the user with no other text.

Automatic fixes

Validated findings—as well as the validation test produced in the previous stage—were passed to a fixer. For this stage we used an internal coding agent (an early version of Ramp Inspect), but you could use a commercially available one. We gave the fixer context on our codebase, coding style, and common pitfalls to avoid.

The fixer wrote a patch based on the detector's suggestion, performing test-driven development using the validator's test. Once the test was passing it opened a pull request. At this point a human team-member took over to review the patch and land the code.

Fixer
The following analysis records a security vulnerability in an endpoint, as well as a test which will pass once the vulnerability is resolved. Read the description and fix the vulnerability as simply as possible. Search the codebase for already existing functional code that can be used, if possible.

Fixing process:
1. Run the test you were given which reproduces the vulnerability, and confirm it fails.
2. Patch the vulnerability, following the tips below.
3. Re-run the test, and confirm it passes. If it does not pass, repeat steps 2 and 3 until it passes. Do not modify the test.

Sometimes the analysis will suggest patching additional findings. If the findings are conceptually related (e.g., a nearby/similar endpoint) you may patch these. If the finding suggests a global codebase audit for more potential errors of a same class, do _not_ do it... stay focused on the task at hand.
