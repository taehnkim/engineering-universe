Apache Arrow Cut Snowflake Fetch Memory Growth by Up to 79%

Dwight Temple

One of our ML training runs was exhausting worker memory before training could even start. A cold fetch of the dataset from Snowflake peaked at 88.8 GiB RSS and forced the job to use a smaller training-data window. This has been a pervasive, mostly unknown limit, across our ML workflows because we've gotten away with scaling our ECS resources as needed.

The clue that something was wrong was the gap between the data we used and the memory required to construct it. Loading the same data from a local Parquet peaked at only 17.6 GiB. That was not an Arrow before-and-after comparison, since the Parquet run skipped the network and database fetch. The 71 GiB gap showed us that something was seriously wrong and a constraint.

Our shared Snowflake-to-pandas path materialized each result as Python objects and SQLAlchemy rows before pandas built the final DataFrame. Those temporary representations required roughly three times the final DataFrame size at peak.

We added an Apache Arrow path for supported reads. Across three query shapes, it reduced median peak process RSS growth by 60–79%. In one large workflow, the lower fetch peak doubled the training-data window on the same cluster size. Existing ML jobs received the improvement without any query rewrites, while unsupported cases continued through SQLAlchemy to keep this seamless for all consumers.

Why the Old Fetch Path Used So Much Memory

The old path did more work than the returned DataFrame showed

Snowflake → Python objects → SQLAlchemy Row proxies → pandas DataFrame

Each representation consumed memory, and much of it existed only long enough to be copied into the next stage. The final DataFrame was only part of the peak.

Snowflake's connector can transfer query results into pandas through Arrow without first constructing a Python object for every value

Snowflake → Apache Arrow batches → pandas DataFrame

SQLAlchemy still handled connections and any read the Arrow path did not support. A read was eligible for Arrow when it used a Snowflake connection, supplied no bound query parameters, and passed no pd.read_sql_query options such as chunksize, index_col, or parse_dates. Cache misses could use Arrow under the same rules; cache hits returned the stored DataFrame. Everything else retained the SQLAlchemy path.

Because our ML jobs already used this common path, making Arrow the default for supported reads did not require query rewrites for anyone.

Benchmark Setup and Results

tracemalloc captures Python allocations, not total process RSS, so we reran the checks with both measurements. We tested a six-column projection over 100,000 rows, a 187-column read over 50,000 rows, and an aggregate query against a wide analytical table similar to the feature datasets used by our ML jobs.

For each query shape, we disabled Snowflake result reuse, alternated which client path ran first, and ran five fetches per path in separate processes. We report medians for peak RSS growth above the post-connection baseline, peak Python allocations, and elapsed time from query execution through DataFrame conversion. These runs measured client-path performance while a separate compatibility procedure checked result equivalence.

Median peak RSS growth was lower for all three tested queries:

  • A narrow six-column, 100,000-row query reduced median peak RSS growth from 111 MiB to 23 MiB and median elapsed time from 3.36 seconds to 2.28 seconds.
  • A wide 187-column, 50,000-row query reduced median peak RSS growth from 914 MiB to 350 MiB and median elapsed time from 12.77 seconds to 5.35 seconds.
  • An aggregate query using AVG, SUM, and COUNT reduced median peak RSS growth from 43 MiB to 17 MiB and median elapsed time from 3.14 seconds to 2.77 seconds.

Peak Python allocations measured by tracemalloc fell by 69–87% across the same runs. The narrow and wide queries completed faster on all five Arrow runs. Aggregate timing results were mixed. Arrow was slower in three of the five run-order comparisons, despite a lower median. Because the timed interval includes Snowflake execution, result transfer, and conversion, we do not use elapsed time as the headline claim.

Making the Change Safe

Adding the connector call was simple, but preserving the pandas contract was not. Arrow and SQLAlchemy can differ in integer widths, aggregate representations, and identifier casing. These are the types of differences that make it painful to drive adoption. To get around these, we normalized those differences in the shared layer to make it seamless.

Equivalence checks covered nine query shapes across four tables with different column widths and data types. Eight matched after normalization. The remaining wide SELECT * represented ten nullable columns differently: SQLAlchemy returned Python None values in object columns, while Arrow used typed float or datetime columns with NaN or NaT. A usage audit found no callers relying on that shape at rollout, and reads that needed the old representation stayed on the SQLAlchemy path just in case.

We also corrected a duplicate-column edge case by normalizing dtypes by column position rather than by label, defined explicit behavior for statements without Arrow result batches, and kept the SQLAlchemy path for reads that still needed row output.

Doubling the Training-Data Window

Lower fetch peaks left more of a worker's memory budget available for the data itself. In one large workflow, the fetch peak decrease was enough to double the training-data window on the same cluster size and move the memory bottleneck from loading data to actually training the model. This was a win in two ways: we could either maintain our existing workflows and reduce cluster size, or we could double our ML workload as needed.

Conclusion

Most of the fetch peak was never the data. Instead, it was the temporary Python objects and SQLAlchemy rows built on the way there, and Arrow skips them.

Because every ML job reads through the same data-access layer, one connector-level change reached all of them. That layer is also where the cost showed up: normalizing dtypes so the pandas contract held, and keeping a SQLAlchemy fallback for the reads Arrow could not serve.

The memory those jobs spent on transient copies now goes straight to training data. The workflow that had been capped got twice the window, and the next ceiling those jobs hit will be in the model rather than the loader. This isn't a revolutionary change, but it is one that lets practitioners stretch their legs and put the compute to use where it matters instead of layers of inefficiencies.
