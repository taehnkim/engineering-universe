Agentic identity: modeling agents to keep users in control

Steve VenzerulRachel Kaplan

With the launch of Ramp for Agents - we now have interfaces (CLI and MCP) that let AI agents work across Ramp cards, bills, expenses, and approvals: customers' agents can now manage money. We needed to model these agents as actors on Ramp — who can transact just like employees can — while creating guardrails to prevent agent misuse or agent confusion.

Our initial model enables human sponsors to easily define and configure their own agents on Ramp while keeping business admins fully in control. Additionally, our design for the authentication flow avoids the need to issue API keys directly to users, eliminating a large class of associated problems. More details below.

Why we needed to build agent identity

The fastest way to ship "agents on Ramp" might have been to help users hand a session token or API key directly to an LLM. But would be problematic:

  • No attribution. Audit logs say a human took an action that an agent actually took. Approval workflows and webhook consumers can't tell the difference.
  • No scoping. The agent gets the full surface area of the human's permissions, even when the user only wanted it to read transactions.
  • No lifecycle. Nothing reminds anyone that an experimental Claude session from six months ago still has full write access.

We built agent identity as a new primitive that maximizes admin and employee sponsor controls.

What is agent identity?

An agent identity is the Ramp record that connects an AI agent to a human sponsor, defines what the agent can do, makes the agent visible in logs and approvals, and gives users and admins a way to expire, revoke or revise its authority.

Our initial version is made up of four key pieces:

  • Agent Key: A unique, named key, tying the agent to a specific user and business on Ramp. This is the "heart" of the identity.
  • Attribution: the Agent Key and actor context let Ramp distinguish the human sponsor from the agent acting on their behalf, so logs and approvals can show “Sarah (via Codex).”
  • Scoping: access scopes define what the agent can do, always bounded by the sponsor’s existing role and capabilities. An agent can never have more access than it's sponsor.
  • Lifecycle: expiration and revocation controls make agent access visible, time-bound, and removable by users or admins.

Architecturally, we've made 2 key decision:

  • We landed on an extension of our existing role-based access control (RBAC) model. The agent's access stems purely from the sponsor user's existing role and capabilities.
  • Agent keys will not become authentication material like other API keys or tokens.

On Behalf Of User (OBOU) vs Standalone Agents (SA)

We could model agents in a variety of ways, but two primary categories emerged: OBOU and SA. In OBOU, the agent is always tied to a human sponsor and acts on their behalf. In SA, the agent is tied to the business and exists outside of any one employee, a "virtual employee" in a sense.

Why we started with building agentic identity on behalf of user (OBOU)

While it was tempting to invest in building out the SA model in which agentic identity is independent from any single user there were practical reasons for us to begin with OBOU

  • Solves most known use cases today: even business-level management can be modeled as on behalf of an admin-level user. Most current demand (Codex, Claude Code, Cursor, home-grown scripts running as me) is OBOU-shaped.
  • Every OBOU action has a human accountable: legacy security, compliance, and legal models at our customers are dramatically simpler.
  • OBOU leaves a human decision-maker in control, making it easier to build trust in what the agent will do.
  • OBOU is a convenient extension of existing user modeling, meaning we were able to re-use auditing and permissioning systems with trivial extensions.

Attribution: "Approved by Sarah (via Codex)"

With an agent acting on behalf of users, there is a temptation to treat the agent like the user themself: when attributing something, you’d simply log the user_id and move on. We rejected this approach because downstream consumers (approval flows, webhook subscribers, finance teams reading the audit log) will be more robust if they can tell that an agent took the action, not the human.

Ramp’s internal logging model already had a concept we call DenormalizedActor—a snapshotted identity attached to every audited event. We extended this data type with an optional AgentContext.

This tweak unlocks niceties like:

  • Low-effort trace-ability. Every operation that is already audit-logged through our standard mechanisms are automatically logged with proper attribution when an agent performs them. This effectively made the full agent request lifecycle as auditable as any other user in the system.
  • One actor type, two display modes. Every existing surface that knows how to render a user actor automatically renders the agent variant as "Approved by Bob (via Claude)" with no per-surface plumbing.
  • Webhooks and eventing gain a typed actor_type field. Downstream systems that consume Ramp webhooks get human plus the agent context, so a customer's own approval workflow can branch on it.

Lifecycle: match how agents work

Unlike full users, today’s agent lifecycles tend to be more ephemeral: you might delegate to an agent to complete some tasks, and then several days later forget it ever existed. Adding smart defaults in the agent key lifecycle improves security and fraud prevention for our users. When designing our agent identity lifecycle, we decided:

  • Expiration by default. All keys are created with an expiration date. We send a reminder ~14 days before expiry so the sponsor can renew, with additional reminders as the date approaches. Renewing a key leaves its value unchanged—ensuring an agent’s stored credential keeps working: this intentionally trades a small amount of theoretical hygiene for a much-reduced burden on key management.
  • Revocation produces data exhaust, including attribution. Users always know who pulled the plug.
  • Notifications fire on creation, expiration, and revocation. A user always finds out when one of their keys changes state, including when they didn't initiate the change.
  • Admin oversight. Admins can view, revoke, or expire any user key in the business. They could also choose to disable the ability to create agent access keys entirely for a given role or user group.

Authentication: minimize risk by treating clients as public

Agent keys are designed to be used by anyone, not just engineers. To reduce risk of mis-handling authentication material, the Agent Keys aren’t actually api keys themselves. Instead, our agent key flow implements OAuth2-PKCE. The Agent Key itself is never used to call Ramp product apis: they can only be exchanged for a short-lived access token—a simple JWT.

Here’s how this works:

  1. The user authorizes their client (CLI, MCP, etc.) via the standard OAuth2-PKCE flow. Users select an existing Agent Key in the process, or automatically create a new one.
  2. Their client is handed an authorization code tied exclusively to the Agent Key selected in step 1 and the ongoing authentication flow.
  3. The client uses the standard OAuth2 Authorization Code flow to fetch an access token and a refresh token. The lifecycle of both is defined by parameters set on the Agent Key, plus some Ramp-enforced minimums.
  4. The client can now call API endpoints normally while the session remains active.
  5. If the access token expires while the agent is running, the standard OAuth2 refresh process applies. Agent Key re-validation during refresh ensures that the access token stays within its bounds.

Leveraging OAuth rather than simple bearer api keys offers several benefits, such as:

  • Reduced blast radius. A leaked access token is bad for an hour (and can be revoked instantly). A leaked API key would have been bad until someone notices.
  • Session semantics for free. Every access token corresponds to both an Agent Key and an initial authenticating user session. This means all api requests can be traced back to an authenticating user’s session, fitting cleanly into existing security and fraud systems originally built for humans.

Notably, Agent Keys do not need to be controlled like API keys. These are really OAuth Key IDs for PKCE under the hood, so a leaked Agent Key itself does not enable any access. Since these are the part of the authentication flow handled by humans (or shared on Slack, etc.) we made them resilient to misplacement.

Release the agents!

Agentic identity modeled as on-behalf of users (OBOU) is optimized for adoption by finance teams: it provides a straightforward, compliance-friendly way for agents to take actions in financial systems and plug into existing paradigms.

With OBOU, agents acting on behalf of admins can take actions on behalf of the entire business.
