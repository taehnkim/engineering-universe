How we built OCA, our AI on-call assistant

Richard MarmorsteinAustin Ray

We built OCA ("On-Call Assistant"), an AI agent that helps with incident response at Ramp. OCA investigates likely causes, shares findings in Slack, answers follow-up questions, and prepares code fixes via Inspect.

At Ramp, we also use our incident flow for customer escalations that need engineering support. We think any organization with a significant on-call burden should invest in an agent like OCA. We’ll show how OCA works today, how we built it, and what we want it to do next.

In the past four weeks, OCA assisted with 575 of the 1,220 PRs merged to address incidents. Among incidents with merged fix PRs, those with OCA-assisted fixes averaged 37% fewer engineers and about 50% less estimated engineer time than the rest. These estimates are based on engineer activity in incident Slack channels. Responders rate OCA helpful 90% of the time.

An OCA investigation

When an incident starts at Ramp, incident.io opens a Slack channel and OCA immediately joins. It starts a thread for its investigation. An interim update usually arrives about 5 minutes after the incident opens, and the finished report typically arrives at about 13 minutes. When there is an obvious code fix, OCA asks Inspect to prepare a PR for human review.

Building OCA

When we started work on OCA, we weren’t sure it was possible for an agent like this to help more than it hurt. Our early investigations with Claude Opus 4.5 would stop as soon as the model found a plausible explanation. We could get it to find mistakes and revise its explanation by asking questions such as, “Did you ground each claim?” and “Did you consult multiple independent sources of evidence?” But results were too inconsistent to trust it to investigate without that guidance. When Opus 4.6 arrived, with a one-million-token context window, agents became able to keep more of the investigation in view, and we began to see a path towards putting OCA in production.

Our first priority was to keep OCA from wasting responders’ time with confident but incorrect explanations. We chose the strongest models and their highest effort settings, and invested heavily in prompts, skills, hooks, and custom CLIs to help it catch reasoning mistakes and incomplete arguments.

These prompts, skills, and tools substantially improved OCA’s investigations with the models we used in the first half of 2026, especially Opus 4.6. When a new model arrives, feature flags let us test which hooks and prompt sections it still needs.

We use Claude Code when running Anthropic models, such as Opus 5, and Codex when running OpenAI models, such as GPT-5.6 Sol. We’ve gone back and forth between them depending on which models are performing better in practice. In the past week, we moved to GPT-6 Astra.

When an incident starts, our service launches Claude Code or Codex in a checkout of Ramp’s application backend monorepo, with OCA’s instructions and investigation tools. Temporal manages the investigation workflow so it can survive worker restarts and deploys.

Session-driven prompting

We wrote much of the prompting system while testing inside active investigations. We designed OCA so it can run as a Claude Code custom subagent. You can run it on your laptop, point it at an incident, and watch its transcript as it investigates. When it makes a mistake, instead of telling it directly what it did wrong, you can review its transcript, tool calls, and evidence trail, identify the general class of error it made, and resume from that point to test prompts designed to help it discover the error itself.

For example, LLMs seem particularly prone to making mistakes around query windows for logs. Query windows often default to a one-hour lookback. An agent will query for an error condition, see that the earliest returned result is from 20 minutes ago, conclude, “The issue must have started then,” and build a theory around a deploy from 20 minutes ago, even when a longer window would show that the condition had been ongoing for some time. We encountered this mistake in live sessions and added lines to our prompt such as, “Before acting on a query result, ask: ‘Could my query be silently excluding the data I’m looking for?’” OCA also has to state the time ranges it queried before it moves on from Datadog.

We use these sessions to develop instructions that help OCA catch mistakes it previously needed human guidance to notice.

Just-in-time instructions

With long sessions, we’ve found results are better when you avoid front-loading all the instructions and deliver them instead at the moment the agent should act on them. When we tested our prompts in live sessions, we weren’t editing the system prompt; instead, we added instructions near the end of the investigation and observed this working well.

We used hooks to deliver those instructions automatically, just before the agent needed to act on them. A tool-use hook can intercept the agent’s attempt to post to Slack and supply an additional prompt: “STOP. Before posting to Slack, you must load the on-call-reasoning-traps skill and run all self-check questions against your current findings.”

The first approach we took with hooks was strict. They completely blocked an agent unless there was proof it had followed an instruction. For example, we would scan the JSONL session log and explicitly check that the agent had loaded a required skill. An agent would sometimes reject the instruction and keep retrying the blocked action. Now our hooks are one-shot “detours.” There are six. The first time OCA tries to post its findings, the hook blocks the post and tells it to cross-check its theory against production Postgres. The next attempt gets the reasoning-traps checklist, then a sanity check, a double check, a review of our Slack posting rules, and a check for a ready-made remediation plan. Each detour fires once. After the sixth detour, the hook allows the post without requiring proof that OCA followed the instructions.

Accuracy vs. speed

Early versions of OCA sometimes investigated for an hour before posting anything. We accepted that delay at first because an incorrect explanation could send responders down the wrong path. But a few months in, we noticed that responders waiting for OCA’s post had been tagging and relying on other fast-responding agents anyway, so we added the interim update, and a hook that, every 10 minutes, adds instructions into the next tool call response to cause OCA to edit its interim post with its current theories. We still want OCA to investigate the cause thoroughly while sharing useful findings and recommending actions early. As newer models came out, we also found that moving from “max” to “high” effort made OCA faster without losing quality, so we use “high” now.

Improvement and evaluation

After every incident, we ask a responder to rate OCA as “Helpful,” “Not helpful,” or “Didn’t read.” This is a coarse signal, but it has been useful for experiments. We’ve used it to evaluate new models, effort/reasoning settings, and experimental features.

One experimental feature is a memory system where OCA can write notes for itself to reference in future investigations. These notes are indexed by metadata such as monitor ID, team, service, or incident lead. Enabling memory doesn’t have a discernible effect on ratings, but does appear to speed up investigations.

We learn the most when responders tell us about specific incidents where they found OCA helpful, frustrating, or inconsequential. There’s an active Slack channel where responders offer suggestions, and OCA’s maintainers spot-check investigations flagged as problematic. For example, responders asked for links to related incidents early in an investigation, and we added them.

Autonomy

Right now, OCA is human-in-the-loop. It has broad, read-only access to the same systems that human responders use when investigating an incident, and its write access is narrowly scoped. It can ask Inspect to open pull requests, but nothing it triggers gets merged without a human. For a limited number of destructive actions, it can ask for human authorization with Slack buttons.

We’re building OCA to handle routine incidents end to end, from creation through remediation, without human involvement. Assisting with almost half of Ramp’s merged incident fixes is a good start, and we think there’s much more we can do here to reduce on-call burden for our engineers, especially as the models continue to improve.
